# R3·R4 병합 전 코드 검토 — Codex

## 결론

**검토 완료, 본편 병합·구현은 보류한다. 실제 Claude 검토가 완료된 것은 아니다.** R3·R4는 별도 claude/r3-r4(9c0fe9d06)에 있고 현재 본편에는 없다. 그대로 합치기 전에 아래 대량 거래 보너스와 검사 환경을 보완하고, 두 UI 충돌을 현재 코드에 맞게 풀어야 한다. D10의 수치나 회복 정책을 새로 정하지 않았다.

R3에는 이미 일괄 거래/흥정 견적 지원이 있다. “한 번 거래”를 “상품 한 개”로 제한하는 새 규칙을 만들 필요는 없다. 핵심 규칙 원본 C#을 별도 임시 폴더에 연결해 **56개 기존 검사 통과**, 추가 대량 보너스 반례도 재현했다. 이는 Unity나 병합된 본편의 실행 검사가 아니다.

검토 기준은 refs.json에 고정한 현재 HEAD와 R3 커밋이다. git merge-tree 결과와 결과 트리를 HEAD와 비교한 changed-files.txt를 보존했다. 실제 작업 폴더·인덱스에 병합하지 않았다. 현재 내용 충돌은 **ContractBoard.cs·TownMarket.cs·Plan.md·WorkLog.md**다. 원래 브랜치의 게임 코드 변경은 C#9파일/새 meta2개이며, 옛 브랜치 파일 전체로 덮어쓰면 안 된다.

## 1. 합치기 전 수정할 경로: 대량 거래 보너스

원본 TownMarket.DrawHaggle은 `int count=RequestedCount`를 확률 계산에 보낸다. 실제 거래 견적은 Market.Preview가 잔고·적재·재고로 수량을 줄인다. 따라서 최대100개를 선택해도 실제로1개만 거래하는 경우, 대량 기준20개 보너스5%p가 붙을 수 있다.

추가 원본 C# 실험 결과(중립·나루/naru·곡식/grain·적당히·게임1일):

| 함수에 전달한 수량 | 성공 확률 | 같은 난수 판정 |
|---|---:|---|
| 1개 | 60% | Refused |
| 100개 | 약65% | Success |

두 시도는 각각 빈 TradeActivity에서 비교했다. 실제1개만 거래 가능한 상황은 호출자 시나리오로 준 것이다. Unity UI/Market.Preview를 이 실험에서 함께 실행한 것은 아니다. UI 호출 경로는 원본 소스에서 확인했다. 원본 HaggleDeal은 마을·품목·방향·날짜만 확인하고 수량 필드가 없다. 성공 뒤 수량을 바꾸어도 DealFor/AppliesTo가 흥정가를 계속 허용한다.

**추천 보완:** 실제 거래 견적의 수량으로 확률을 계산하고, 성공한 흥정을 그때 확정한 품목·방향·실수량에 연결한다. 수량/방향/품목을 바꾸면 해당 견적의 유효성을 다시 확인한다. 할인으로 구매 가능한 개수가 늘어나는 경우도 포함해 확정 수량과 최종 실행 수량을 일치시킨다. D10의20개/5%p 자체는 바꾸지 않는다. 새 일괄거래 제한을 사용자 대신 확정하거나 구현하지 않았다.

근거: 원본 HaggleRules.BulkCount/Chance, TownMarket.DrawHaggle·DealFor·TradeBatch, HaggleDeal.AppliesTo. 실행 결과는 bulk-counterexample.json이다.

## 2. 저장 실패 처리 — 실행 검증 필요

9c0fe9d06은 게시판 수락·납품 뒤 SaveNow를 호출하지만 반환 bool을 확인하지 않는다. 정상 쓰기를 가정한 즉시 저장 연결은 있으나, 디스크/저장 차단 실패 때도 화면이 수락·반환 성공으로 이어질 수 있다.

이는 정적 코드 관찰이며 실제 Unity 저장 실패를 주입하지 않았다. 무조건 손실/중복 지급이 발생한다고 판정하지 않는다. 병합 뒤 실패 주입으로 확인하고, 실패를 알리며 계약 목록·보증금·완료 상태가 서로 어긋나지 않게 처리해야 한다. 돈만 되돌리고 계약을 남기는 원복은 피한다.

현재 사용자 저장9파일의 관련 필드만 읽었다. 비어 있지 않은 R3/R4 기록과 속죄 계약은0개였고, 이전 UI 점검 백업 대비9파일 해시도 그대로였다. 실제 사용자 슬롯으로 이주 시험을 하지 않았다. R3 저장을 R3 코드가 없는 구버전에서 다시 저장하는 역방향 사용은 새 필드 보존을 따로 보장하지 못하므로 호환 시험은 분리된 슬롯에서 한다.

## 3. 검사 환경 문제 — 원래 프로젝트 그대로는 실패

이 Mac은 .NET SDK10.0.401/참조 팩10.0.12만 있다. 원본 StandingProbe.csproj는net8.0을 대상으로 하고 NuGet 소스를 비운다. 원본 프로젝트 그대로 실행하면 .NET8 참조 팩을 찾지 못해 **NU1100으로 실패**했다(original-target.log).

원본 규칙5개 파일과 원래 Stubs/Program을 임시 폴더에 추출하고, **임시 csproj의 대상만net10.0으로 바꾸어** 기존56검사를 실행했다. 게임 규칙 코드는 수정하지 않았다. 추가 반례는 임시 Program만 바꾸어 실행했다. 따라서 “원래net8 프로젝트 통과” 또는 “Unity 통과”로 기록하면 안 된다.

기존 test_r3_r4_rules.py는 dotnet이 없거나 NU1301일 때만 건너뛰므로, 이 Mac의 NU1100은 그대로 실패가 된다. 병합 시 사용할 SDK/참조 팩을 명시하거나 검사 도구가 설치된 팩으로 실행되게 정리한다. 진짜 규칙 실패를 무조건 skip하는 식으로 바꾸지 않는다. SDK나 패키지를 새로 설치하지 않았다.

재현: `python3 Tools/Integration/review_r3_r4_core.py --ref 9c0fe9d06`. source-manifest.json에 원본 코드 지문·원본/검토 대상 프레임워크를 기록했다. 이 도구는 본편 소스를 가져오지 않고 임시 폴더를 정리한다.

## 5. Claude에게 넘길 순서와 완료 확인

1. 수량 보너스 보완 방향과 저장 실패 대응을 확인하고,9개 C# 변경을 현재 코드에 결합한다. 자동 병합된 파일도 검토하며 Docs/Standing.md는 Claude가 현재 결정과 대조한다.
2. 승인 게시판 레이아웃, UI 잠금 중 모터 정지, 우물3냥 기록·현재 지도/ID/저장 참조를 보존한다. 지형/에셋/빌드 목록을 다시 만들지 않는다.
3. 수량1/19/20/100, 부족한 돈/재고/적재, 흥정 후 수량 변경, 할인 뒤 추가 구매 가능 경계를 검사한다. 실제 견적과 실행의 수량/금액을 비교한다.
4. 같은 마을 매입 후 재계산 되팔기0이하, 흥정 실패 일일 잠금/3시간 금지·평판 불변을 검사한다. 단순히 견적 두 개를 비교하는 검사로 대신하지 않는다.
5. 마이너스 회복3경로/중립 상한·문명별/중앙 마을별 독립, 일반/속죄 수락·납품·실패·보증금/재개방 저장을 실제 임시 슬롯으로 확인한다. 저장 실패도 주입한다.
6. 설치된 검사 환경을 확인한 뒤 전체 unittest 두 환경/Unity8종을 실행하고 실제 집계로 기록한다. 이번56규칙 검사로 병합 후 검사나 사람 플레이를 대체하지 않는다.
7. 현재 화면 크기의 흥정·회복·게시판 캡처를 사용자에게 보여 주고 승인 범위를 기록한다. 팀 통합은 별도 사전·완료 카톡 절차를 따른다.
