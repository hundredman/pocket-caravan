# 숲 겹침 성능 검토 — 2026-10-29

검토 완료, 본편 변경 없음. **나무를 겹쳐 숲을 만드는 방식은 유지해도 된다. 다만 고려 타일 텍스처를 묶는 최적화를 다음 성능 작업으로 권장한다.** 이번 검토만으로 실제 게임에 렉이 없다고 판정하지는 않는다.

## 확인한 구조

- `Tools/WorldLayout/m1_tiles_preview.py:496`부터 나무를 통째로 뒤→앞 순서로 합성한다. 이 작업은 Python 맵 생성 단계다.
- `m4_export.py`가 합성 결과를 16×16 칸으로 내보내고 RGBA 내용이 같은 타일은 재사용한다. 플레이 중 겹친 나무 원본을 매 프레임 다시 합성하지 않는다.
- `MapJsonBuilder.cs`는 Ground/Deco/Objects/Above의 네 Tilemap에 타일을 넣는다. 13개 본편 씬 모두 Chunk 모드, 청크 크기 (32,32,32). 청크 하나가 반드시 그리기 호출 하나라는 의미는 아니다.
- Blocked Tilemap은 렌더러가 없고, MapRoot의 이동 판정은 HasTile 조회다. 조사한 씬의 Collider2D는 모두 0개. 숲 나무마다 물리 충돌체나 Update를 붙이는 구조는 아니다. 씬의 개별 SpriteRenderer 숫자는 NPC·소품 등을 포함하므로 숲 나무 수로 세지 않았다.

## 정적 검사 / Unity 씬 조사

`Tools/Performance/forest_audit.py` 실행 성공. 13개 JSON·씬과 주요 생성 원본이 활성 Unity 체크아웃과 일치하는지 SHA로 확인했다. 이미지 동일성은 아래 Unity 실험과 별도 Python 확인에서 크기+디코딩 RGBA로 검사했다.

| 항목 | 결과 |
|---|---:|
| 13맵 전체 고유 타일 이미지 | 1,327종, 전부 16×16 |
| 전체 순수 RGBA 픽셀 용량 | 1,358,848 bytes (약 1.30 MiB) |
| 송악 씬 타일 텍스처 | 689개 / Unity 보고 약 1.93 MiB |
| 중앙 진입 씬 타일 텍스처 | 643개 / Unity 보고 약 1.80 MiB |
| 각 씬의 타일 텍스처 범위 | 300~689개 / 약 0.84~1.93 MiB |
| 가장 조밀한 30×17칸 창 | 송악 502/510, 중앙 진입 490/510칸에 숲 합성 포함 |
| 해당 창의 고유 타일 이미지 | 송악 153종, 중앙 진입 175종 |

RGBA 용량은 메모리 전체가 아니다. Unity 보고 수치도 텍스처 객체만이며 Tile·Sprite·씬·드라이버 전체 사용량은 아니다. 에디터 preview 열기 시간은 캐시/에디터 영향을 받아 게임 맵 전환 시간으로 해석하지 않는다. 기존 Venice atlas가 있어도 이번 두 씬의 조사 대상 타일 sprite.packed는 모두 false였다.

## Unity 임시 비교 실험

Unity 6000.3.26f1 / Apple M3 Pro / Metal / 18GB, **Edit 모드**. 실제 본편 씬을 OpenPreviewScene으로 열고, 두 조밀한 창을 480×270으로 렌더링했다. 원래 활성 씬은 그대로 보존했다.

타일만 비교하기 위해 preview의 개별 SpriteRenderer와 조명을 끄고, 프로젝트에 있는 Sprite-Unlit-Default 재질을 임시 적용했다. 따라서 본편 조명·NPC·UI를 포함한 게임 화면/FPS 측정이 아니다. 렌더 요청+GPU 화면 읽기+Texture Apply를 동기적으로 재는 지표이며, CPU/GPU 각각의 순수 프레임 시간도 아니다.

각 경우 워밍업 후 20회, 원래 텍스처 → Objects/Above 숨김 → 임시 atlas → 원래 텍스처 복구 순으로 측정했다.

| 지형 렌더+화면 읽기 중앙값(ms) | 원래 | Objects/Above 숨김 | 임시 atlas | 원래로 복구 |
|---|---:|---:|---:|---:|
| 송악 숲 | 17.32 | 5.66 | 4.71 | 19.69 |
| 중앙 진입 숲 | 10.21 | 3.74 | 4.52 | 10.34 |

- 씬 타일 텍스처 689/643개를 메모리에서만 512×512 한 장으로 묶었다. 타일 확대/축소 0, 입력 타일 RGBA 변화 0, 두 비교 화면 전체 RGBA 차이 0.
- **텍스처 분산을 줄일 가치가 있다는 근거**다. 이 수치의 비율을 실제 게임 FPS 향상률로 환산할 수 없다.
- atlas 텍스처의 Unity 보고 메모리는 약 2.00 MiB로, 기존 두 씬보다 작지 않았다. 이번 실험은 메모리 절감의 증거가 아니다.
- Objects/Above 숨김은 숲 외 물체 타일도 제거하므로 숲만의 정확한 비용이 아니다.
- UnityStats의 drawCalls/batches는 모든 실험에서 85로 고정됐다. 동기 수동 렌더에 대응하지 않는 값이어서 호출 수 감소 근거로 쓰지 않았다.
- 초기 lit 실험에서는 원래 씬과 preview의 Global Light 중복 경고가 나왔다. preview 조명만 끈 중간 실험은 검게 촬영되어 폐기했다. 위 표·JSON·PNG는 **검게 나오지 않는 최종 unlit 실험**만 사용한다. 경고가 있었으므로 ‘콘솔 오류 0’은 주장하지 않는다.
- preview 닫기·임시 Tile/Sprite/Texture/Material 해제 후 원래 씬 경로와 dirty 상태가 보존됨을 코드로 확인했다. Play 진입·저장 파일 접근·본편 에셋/씬 쓰기 0.

## 권장 후속 작업과 한계

후속 [13맵 회귀 검사](../Forest-Atlas-Regression-2026-10-29/README.md)에서 비정수 축소 전체 보기5맵의 픽셀 차이를 발견했다. 여백 보강으로 검은 격자선은 제거했으나 재검사 후3맵에 소수 픽셀 차이가 남았다. 아래 atlas 최적화 권장은 이 차이를 해소하고 다시 검사한다는 조건이다. 두 창의 통과를 모든 배율의 동일성으로 해석하지 않는다.

1. 숲 밀도와 승인 그림은 유지한다. 나무 수를 줄이거나 숲 그림을 다시 만들 이유는 이번 검토에서 찾지 못했다.
2. 고려의 합성 타일을 Sprite Atlas로 묶는 작은 최적화 작업을 권장한다. Point/no mipmap·회전/타이트 패킹·투명 경계·장면별 로딩을 검토하고, 기존 타일 ID와 저장 데이터를 유지한다.
3. 본편에 적용할 때 13맵 RGBA 회귀와 실제 조명·가림을 다시 검사한다. 현재 화면 동일성 통과는 unlit 두 창에 한정된다.
4. 실제 Play에서 이동·맵 경계 전환의 CPU/GPU 프레임·GC·메모리·그리기 호출을 확인해야 최종 판정할 수 있다. 이번에는 실제 플레이, 목표 저사양 기기, 빌드 측정을 하지 않았다. 저장 데이터/부트스트랩 영향 없이 조사하려고 Edit 모드로 범위를 제한했다.
5. 새 산맥/논 승인 시안은 본편 미적용이므로 이번 13맵 측정에 포함하지 않았다.
