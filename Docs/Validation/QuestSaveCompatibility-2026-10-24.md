# 퀘스트 저장 호환 검증

2026-10-24, Codex. 사용자의 '뭐가 문제인지 제대로 확인' 요청에 따른 후속 검증이다.

## 결론

**현재 정의를 바꾸지 않는 저장·복원과, Q1에서 목표를 바꾼 뒤의 호환은 다르다.** 같은 정의의 목표 복원, 수락 보상 보존, 완료 기록 보존은 확인했다. 목표 정의를 변경할 때는 다음 문제를 실제 프로젝트 C#의 분리 실행으로 재현했다.

| 상황 | 현재 동작 | 문제 |
|---|---|---|
| 같은 ID의 목표 순서/대상 변경 | 저장된 step을 새 objectives 배열에 그대로 사용 | 예전 1번 '객주와 대화'가 새 1번 '장단 방문'이 돼도 검사 통과 |
| 목표 종류 변경 | 저장된 amount도 그대로 사용 | 예전 목표에서 쌓은 진행량 2가 새 판매 목표의 2개로 해석됨 |
| 목표 수 축소 후 step == 새 목표 수 | 범위 검사 통과, Import 후 Done이지만 active에 남음 | Current가 null이고 Tick도 완료 처리하지 않아 보상·종료 없이 멈춤 |
| 목표 수 축소 후 step > 새 목표 수 | 저장 호환 검사에서 거절 | 원본을 지키는 안전 장치지만, 이주가 없으면 옛 진행으로 이어 할 수 없음 |

이 재배치 예시는 진단용 퀘스트 정의다. 아직 작성되지 않은 Q1 새 설계를 이미 게임에 적용했거나, 사용자의 실제 저장이 손상됐다는 뜻은 아니다. **목표를 바꾸기 전에 대응해야 하는 실제 호환 결함**이다.

## 이미 보존되는 것과 앞선 설명의 정정

- 같은 정의의 활성 단계가 같은 목표를 가리키는 것은 보존된다.
- `rewardCaptured`가 있으면 현재 보상 수치 대신 수락 당시의 money/credit을 보존한다.
- 캡처 필드가 없으면 authored legacyReward 값으로 복구하는 경로가 있다.
- 완료한 퀘스트 ID는 완료 상태로 복원되고 재수락할 수 없다.
- 현재 맵이 방문 목표이면 `CheckPassive`가 Tick에서 처리한다. '이미 목적지에 있어도 반드시 재입장해야 한다'는 일반화는 틀리다. 과거 방문한 뒤 다른 곳으로 간 경우의 기록 기반 인정 여부는 Q1 설계 선택이다.
- 실제 저장의 이미 쌓인 신용 보존과, 미완료 퀘스트가 앞으로 줄 신용을 평판으로 바꿀지는 다른 정책이다. 후자는 R6에서 정해야 한다.

## 검사 방법과 한계

`Tools/Integration/QuestSaveProbe`는 원본 `QuestManager.cs`, `QuestData.cs`, `GameEvents.cs`, `SaveCompatibility.cs`, `SaveSystem.cs`를 직접 연결해 .NET 10에서 실행한다. 주변 Unity/게임 객체만 대체했다. 진단용 목표 변경 사례와 현재 퀘스트 에셋의 목표 배치를 검사한다. 현재 에셋 12개·유효 활성 단계 21개를 목표 타입/대상/필요량 기준으로 복원했고 총 10개 관찰 항목을 기록했다. 결과는 [JSON](Quest-Save-Probe-2026-10-24.json)에 있다.

Unity 연결을 시도했으나 project/info 및 execute_code가 'No Unity Editor instances found'를 반환했다. 따라서 Unity JsonUtility 직렬화·씬·플레이·실제 저장 파일로 확인했다고 쓰지 않는다. 테스트에서 실제 저장 경로와 직렬화 호출은 예외로 막았다. 사용자의 저장 파일은 읽거나 수정하지 않았다.

원본 코드:

- `QuestManager.Save/Import`: 퀘스트 ID, step, amount, 보상만 저장·복원한다. 목표 ID/정의 버전이 없다.
- `SaveCompatibility.Validate`: `step >= 0 && step <= quest.objectives.Count`만 범위 검사한다. 같은 step의 의미 변화나 끝난 단계의 활성 상태를 검증하지 않는다.
- `QuestManager.Tick/CheckPassive`: Current가 null이면 반환한다. Import는 Done인 활성 기록을 정리하지 않는다.

진단 출력의 `observed: true`는 현상이 재현됐다는 뜻이며 결함 수정 완료를 의미하지 않는다. Unity 대체 객체와 에셋 목표 배치 검사는 전체 게임 데이터 GUID 연결을 검증하지 않는다.

## Q1/B6에서 처리할 방향

1. 현재 퀘스트별 목표 정의를 이주용 기준으로 보존한다. 기존 ID만 남기는 것으로 끝내지 않는다.
2. 앞으로는 목표에 안정적인 식별자와 콘텐츠 버전을 두고, 순서를 바꿔도 동일 목표로 연결한다. 구 저장의 정수 단계는 이전 정의→새 목표 대응표를 통해 옮긴다.
3. 진행량은 같은 의미의 목표일 때만 옮긴다. 목표 종류·아이템·대상·필요량이 달라진 경우 별도 이주 규칙을 사용한다.
4. 제거한 목표·종료 단계·완료 퀘스트는 이주 정책으로 처리한다. 빈 활성 상태를 방치하거나 무조건 보상을 다시 주지 않는다. 판단할 수 없는 저장은 이유를 안내하며 원본을 보존한다.
5. 수락 당시 보상은 현행 보존 장치를 유지하고, R6 신용→평판 전환 예외를 명시한다.
6. 적용 전후 동일 단계, 중간 진행, 목표 삭제/추가/순서 변경, 완료 기록, 재로드, 중복 지급, 현재 위치 선방문을 검사한다.

새 Q1 목표·보상 정책이 아직 없으므로 대응표를 임의로 작성하거나 런타임 이주를 구현하지 않았다. 이 문서는 Q1/B6의 인수 조건과 재현 근거다.
