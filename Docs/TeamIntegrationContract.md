# 지역 통합 규칙 — 팀 합의안

> **10월17일 전체 재대조 교정:** 스타팅 지역은 수도1+수도 외 최소 마을4, 이미 발전한 지역·자유 이동·마을 등급/개인 신용별 시설 이용이 제작 범위다. 현재 고려 네 맵은 수도1+마을2+길1로 미달이다. [전체 누락 교정](FullRequirementsReview_2026-10-17.md)와 [고려 제작 명세](GoryeoRegionSpec.md)를 우선하며 이전 최소 거점/미정/검토 중단 표현을 현재 범위로 재사용하지 않는다.

최신 능력·운반 정책은 [10월17일 변경 요약](DesignUpdate_2026-10-17.md)을 따른다. 네 지역이 동시 개발 중이며 현재 좌표·ID 계약은 기존 출신 ID 변경을 뜻하지 않는다.

2026-10-17 구현 후속: 지역별 등록 JSON, 명시적 RegionData/NPC/씬 경로, 공용 맵 목록 소비와 통합 검사를 적용했다. 현재 적용 경로는 [팀 개발 시작 안내](TeamDevelopment.md)를 우선한다. 아래의 미적용 설명은 이전 검토 시점 기록이며, 경제 거리·아트/지도·온라인 등 남은 이관 전체가 완료된 것은 아니다.
기준일: 2026-10-17. 사용자에게 전달된 팀 피드백을 바탕으로 정리한 **합의안**이다. 좌표 배정·이름 규칙을 팀이 최종 승인했거나 게임에 적용한 상태는 아니다. 기존 고려 ID·좌표·씬·저장은 이번 정리에서 변경하지 않는다.

## 1. 먼저 맞출 세 가지

| 항목 | 제안 | 통합 전에 확인할 것 |
|---|---|---|
| 좌표 구역 | 고려 x=0~9, 베네치아 10~19, 아라비아 20~29, 북유럽 30~39 | y 사용 범위, 중간 구역 담당/구역, 좌표와 경제 거리의 분리 여부 |
| 새 ID 접두어 | `goryeo_`, `venice_`, `arabia_`, `north_` | 상품·마을·NPC·퀘스트·새 맵의 ID 목록과 기존 ID 호환 |
| 접속부 | 출구와 도착 스폰을 구분하고 연결표에 등록 | 목적 씬, 목적 스폰, 폭·방향, 역방향 연결, 제작 담당 |

지역 담당은 고려 은샘·베네치아 윤채·아라비아 은인·북유럽 기우다. 공통 기능 담당을 이 지역 배정으로 자동 결정하지 않는다.

## 2. 좌표 구역과 실제 이동은 별개

현재 `World/Regions/goryeo.json` 등록부와 생성 `WorldIndex.asset`에서 고려는 다음 네 좌표를 사용한다. 이전 `MapJsonBuilder.MapCoords` 고정 목록은 공통 등록부로 대체됐다.

| mapId | 좌표 |
|---|---|
| `Naru` | (0,0) |
| `Route01` | (1,0) |
| `Gaegyeong` | (2,0) |
| `Dakmok` | (3,0) |

새 배정은 우선 **충돌 없는 논리 좌표를 예약**하는 용도다. 같은 (x,y) 중복을 막고, 새 맵은 담당 구역 안에서 좌표를 등록한 뒤 제작한다. y 범위와 중간 구역 좌표는 아직 제안되지 않았으므로 임의로 확정하지 않는다. x 열이 열 개라고 지역 맵을 열 개로 제한하는 뜻은 아니다. 확장 시 y나 추가 구역을 합의해 사용한다.

이 구역을 나눴다고 고려와 베네치아가 곧바로 이어지지 않는다. 실제 이동은 출구 연결 그래프로 정하며, 다른 문명 사이에는 여러 중간 구역을 둔다. x 차이가 곧 실제 지나가는 맵 수라는 뜻도 아니다.

**경제 영향:** 현 `ItemData.MapsFrom()`은 `TownData.worldCoord`의 맨해튼 거리(|dx|+|dy|)로 상품 기준가의 거리 가산을 계산한다. 예를 들어 산지 (0,0)에서 장터 (30,0)으로 잡으면 거리가 30으로 계산된다. 담당 구역 번호만 보고 이 값을 입력하면 실제 교역로 길이와 무관하게 시세 차익이 커질 수 있다. 기존 고려 거점 좌표와 맵 좌표는 일치시켜 쓰고 있으므로 어느 한쪽만 바꾸어 문제를 숨기지 않는다.

팀 결정 전에는 기존 고려 좌표를 유지한다. 문명 간 가격을 붙이기 전, ① 논리 배치 좌표와 경제 거리 데이터를 분리할지 ② 실제 교역 연결에 따른 거리를 사용할지 결정하고 기준가·의뢰 보수·기존 저장 영향을 검증한다. 자동 경로 비용 계산은 아직 구현된 기능이 아니다.

지도 UI는 별도 `GoryeoLayout.json`과 출구 정렬을 사용한다. 논리 좌표 구역 배정만으로 지형 지도와 연결도가 자동 생성되는 상태는 아니다.

## 3. ID 규칙과 기존 데이터 보호

- 새 지역 콘텐츠 ID는 소문자 영문·숫자·밑줄을 사용한다. 예: `north_fur`, `north_port`, `north_merchant_01`, `north_delivery_01`.
- 표시 이름은 별도 필드로 관리한다. 한글 지명을 바꿔도 ID를 바꾸지 않는다.
- ID 유일성은 종류별로 확인하고, NPC나 퀘스트를 복사할 때도 원래 ID를 그대로 가져오지 않는다.
- 기존 고려의 `Naru`, `naru`, `gaekju`, `salt` 같은 ID는 호환 대상으로 등록한다. 접두어를 맞추겠다고 일괄 변경하면 퀘스트·지도·저장·데이터 조회가 끊길 수 있다. 변경이 필요하면 이전→새 ID 이주표를 먼저 만든다.
- 기존 공통 수단 `walk`, `handcart`와 여러 지역이 쓰는 상품은 공통 담당이 정의를 소유한다. 지역마다 같은 기능을 새 ID로 복제하지 않는다.
- 같은 소금 상품을 여러 장터가 판매한다면 기존 공통 상품을 참조한다. 산지·무게·품질이 다른 별도 상품으로 기획한 경우에만 `venice_salt` 같은 새 ID를 만든다. 접두어는 중복 충돌을 막는 규칙이며 상품 설계를 대신하지 않는다.

파일·폴더 이름만 바꾸는 것과 데이터 내부 ID 변경은 다른 작업이다. 새 에셋의 `.meta`도 함께 전달하고 기존 GUID를 덮어쓰지 않는다.

## 4. 출구와 도착 스폰 계약

`North_GateS` 같은 이름을 먼저 합의하는 방향은 유효하다. 다만 지역 전체에 남문이 하나뿐이라는 전제에 의존하지 않도록 **맵 ID와 번호를 포함**하는 안을 권장한다.

| 구분 | 새 콘텐츠 이름 예시 | 의미 |
|---|---|---|
| 맵 ID | `north_port` | 지역의 한 맵 |
| 출구 논리 이름 | `north_port_exit_s_01` | 이 맵 남쪽의 1번 출구 |
| 도착 스폰 ID | `north_port_spawn_s_01` | 이 맵 남쪽에서 들어와 서는 위치 |

방향은 플레이어 이동 방향이 아니라 **해당 맵의 경계**다. 북쪽으로 나간 뒤 다음 맵의 남쪽 스폰에 도착하는 연결이 가능하다. 복수 출구는 번호로 구분한다. 기존 `S0`, `E`, `W`, `N`, `S` 스폰은 현재 참조를 유지한다. 특히 `S0`는 시작 스폰으로 코드에서 사용하는 값이다.

현행 맵 JSON은 출구의 `target`에 목적 씬 이름, `spawn`에 **목적 맵의 도착 스폰 ID**를 넣는다. 빌더는 이를 `MapExit.targetScene`, `targetSpawnId`에 전달한다. 현재 출구의 `id`는 런타임 출구 식별자로 전달하지 않으므로 이름만 추가해 자동 연결된다고 보지 않는다. 출구 논리 이름은 우선 연결표에서 관리하고 런타임 필드 도입은 별도 구현이다.

연결표 필수 열:

`출발 mapId / 출구 이름 / 출발 경계·타일 범위 / 목적 scenePath·씬 이름 / 목적 mapId / 목적 spawnId / 도착 타일 범위 / 역방향 연결 / 담당 / 검증 상태`

현재 실제 연결 예시는 `Naru` 동쪽 출구 → `Route01` 씬의 `W` 스폰이다. 역방향은 `Route01` 서쪽 출구 → `Naru` 씬의 `E` 스폰이다. 이 연결을 새 규칙을 설명하기 위해 변경하지 않는다.

양쪽 통로 폭과 스폰 폭·축을 맞추고, 수레가 벽·물·출구 트리거에 겹치지 않는지 왕복 확인한다. JSON 타일 y는 위에서 아래로 증가하고 Unity 셀 y는 아래에서 위로 증가하므로 같은 숫자를 그대로 복사하지 않는다. 목표 씬이 빌드 목록에 포함되는지도 검사한다.

## 5. 납품과 통합 순서

1. 팀이 위 세 가지와 y·중간 구역 구역, 경제 거리 기준을 승인한다. 각자 ID·맵·좌표 목록을 제출한다.
2. 지역별 등록부에 `regionId`, mapId, scenePath, 좌표, 원본 파일, 담당, 콘텐츠 버전을 기록한다. 등록부를 읽는 공통 빌더/검사는 구현돼 있다. 원본 소유자/콘텐츠 버전의 추가 필드는 별도 과제이며 현재 스키마는 TeamDevelopment.md를 따른다.
3. 연결표로 한 쌍의 접속부를 정하고, 양쪽 출구·스폰을 왕복한다. 지역 하나를 복사한 것만으로 통합 완료로 처리하지 않는다.
4. 퀘스트·상점·상품·저장 참조, 시작 위치, 지도 표시, 가격 영향을 확인한다.
5. 새 지역은 이미 공통화한 등록부/빌더에 연결한다. 지역 아트·지형 지도·가격 거리·시작 출신/시설 등 남은 전용 결합을 검증한다. 좌표·접두어 세 가지만 맞추면 자동 병합되는 상태는 아니다.
6. 온라인 연결 후에는 서버와 클라이언트가 같은 콘텐츠 버전을 사용하는지 확인하고 지역 전환·재접속 후 돈과 화물이 유지되는지 별도로 검증한다.

원본 편집 규칙과 더 긴 이관 계획은 [지역 제작 설계안](RegionAuthoringPlan.md)을 따른다. Unity에서만 수정한 생성 씬은 재생성 시 사라질 수 있으므로 납품 원본을 먼저 정한다.

## 6. 발표 일정의 상태 표기

10월19일 발표에서 10월18일까지의 작업을 남겨 두는 것은 가능하다. 해당 행을 **사전 준비**로 구분하고 실제 상태를 함께 쓴다. 날짜가 지났다는 이유만으로 완료 처리하지 않는다.

10월17일 확인 기준 문구:

- 기획 초안 정리: 완료. 팀의 최종 범위 승인과 구분한다.
- 고려 로컬 교역: 구현. 밸런스·재미·모든 오류의 검증 완료를 뜻하지 않는다.
- 좌표·ID·접속부 규칙: 합의안 작성. 팀 최종 승인·게임 적용은 별도다.
- 온라인 연결 시험: 검증 대기. 기존 문서상 온라인 기능은 미구현이며 새 접속 시험 결과가 없다.

발표 직전 실제 시험을 통과했다면 날짜·빌드/커밋·실제 인원·성공 범위를 기록하고 해당 항목만 완료로 바꾼다. 두 클라이언트 접속 성공과 공유 거래·저장·재접속 완료를 구분한다.
