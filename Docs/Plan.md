# 작업 계획

정리: 2026-10-24. 범위는 은샘 담당(고려 + 중앙 대륙 동쪽)의 배경·맵·아트 재정비와 중앙 대륙 시스템이다.
Codex와 Claude가 아래 [에이전트 분담](#에이전트-분담)에 따라 자기 작업을 골라 이어서 할 수 있게 적는다.

**개인 작업 우선 (2026-10-24 사용자 지시)**
- 고려·중앙 대륙 동쪽 개인 작업을 먼저 완료하고, 팀 공통 온라인·채팅·출신 선택 화면 등은 이후에 시작한다. 게임 진행·재산을 실제로 손상시키는 문제 외의 공통 미구현 사항은 후속 작업이다.
- 현재 작업에서 목표를 바꿀 때 생기는 퀘스트 저장 이주는 Q1/B6 안에서 해결한다.
- A1·A4·C1~C5의 제작/교체 아트는 **은샘 검토 필수**다. 자동 검사나 Claude 검토만으로 완료 처리하지 않는다.

**사용 규칙**
- 작업을 시작하면 상태를 `진행 중`으로, 끝나면 `완료`로 바꾸고 [작업 기록](WorkLog.md)에 한 줄 남긴다.
- `결정 대기`에 걸린 작업은 시작하지 않는다. 결정이 나면 결정 표를 먼저 고친다.
- 완료 기준을 실제로 확인하지 못했으면 `완료`로 바꾸지 않는다. 확인하지 못한 항목을 작업 기록에 적는다.
- 새 작업이 생기면 같은 형식으로 표에 추가하고, 에이전트 분담 표에도 담당을 적는다. 작업 ID는 다시 쓰지 않는다.

## 에이전트 분담

두 에이전트가 같은 작업을 동시에 잡지 않도록 담당을 나눈다. **자기 담당 작업만 고른다.** 다른 쪽 작업이 막혀 있어도 대신 하지 않고, 작업 기록에 막힌 이유를 남긴다. 담당을 바꿀 때는 은샘이 이 표를 고친다.

- **Claude (Pro):** 판단과 설계만. 아트 요청서 작성([ArtBrief](ArtBrief.md)), 퀘스트·평판 수치 설계, 결정 항목 정리, **단계가 끝날 때의** 화면·구조 검토. Claude 작업은 한 번에 쓰는 양이 커서(이미지·Figma·기기 연결) 기계적인 일은 맡기지 않는다.
- **Codex (Plus, gpt-6.1 sol):** 범위가 분명한 구현과 **아트 제작**(2026-10-24 변경: AI 이미지 생성·정리 도구·Aseprite를 맥에서 직접 쓸 수 있어 Codex가 맡는다. 판정은 은샘이 그림으로). 런타임 시스템, 에디터 도구, 맵 생성기, 세계 배치 원본, 아트 정리 도구, 저장 이주, 테스트.

## 동시 진행과 사용량

**갈래.** 작업은 서로 거의 독립된 갈래로 나뉜다. **갈래 안에서는 선행 순서대로, 갈래끼리는 동시에** 진행한다.

| 갈래 | 순서 | 주 담당 |
|---|---|---|
| 아트 | A5 도구 → C1 사람 NPC 3명 시험 → C2·C3 기와집·나무 1개씩 시험 → (은샘 승인) → 나머지 C·A4 → C6 | Codex (요청서는 Claude, 승인은 은샘) |
| 맵 | (D9) → B1 → B2 → B3·B4 → B5 → B6 | Codex |
| 평판·신용 | R1 → R6 / D10 효과표 → R2 → R3·R4 | Codex (효과표는 Claude) |
| 중앙 대륙 | B1 → E1 / B4 → E2 → E3·E4 | Codex |
| 퀘스트 | Q1 설계(완료) → R6 후 Q1 구현 | 설계 Claude → 구현 Codex |

**넘겨주기 형식 (Claude → Codex).** 설계를 넘길 때는 번호 붙은 단계, 고칠 파일, 완료 확인 방법(실행할 검사 명령)을 적은 문서로 남긴다. Codex는 그 문서만 읽고 시작할 수 있어야 한다. Codex가 판단이 필요한 문제에 막히면 직접 정하지 말고 작업 기록에 상황을 적어 Claude 검토로 넘긴다.

**검토 시점.** Claude는 작업마다가 아니라 갈래의 한 단계가 끝났을 때(예: R1+R6, B1, B2) 한 번에 검토한다. 검토는 diff·테스트 결과·작은 PNG로 하고, Figma는 사용자 결정이 필요할 때만 쓴다.

**사용량 (2026-10 기준).**
- 둘 다 5시간마다 다시 차는 한도와 주간 한도가 있다. Claude Pro는 claude.ai 채팅과 한도를 같이 쓴다. Codex Plus는 모델마다 5시간당 메시지 수가 다르고, 클라우드 작업도 같은 한도를 쓴다.
- Codex에서 단순·반복 작업은 더 가벼운 모델로 돌리면 한도를 아낄 수 있다.
- 한 세션에는 작업 하나. 세션 시작 때는 이 문서와 작업 기록 마지막 줄만 읽고 들어간다.

**Codex 주간 한도는 남는 경우가 많다.** 주간 사용량이 자주 초기화되어 왔다(5시간 한도는 아님). 그래서 Codex는 사실상 5시간 한도가, Claude는 주간 한도가 먼저 막힌다고 보고 계획한다.
- 일을 더 Codex 쪽으로 싣는다. 기계적으로 할 수 있는 조사·계산·검사는 Codex가 먼저 하고, Claude는 그 결과로 판단만 한다(위 A3a·R2 수치 계산처럼).
- Codex는 5시간 창마다 꾸준히 쓴다. 큰 작업은 창 하나에 끝나는 크기로 나눈다.
- 초기화는 보장된 것이 아니다. 남는 사용량을 전제로 마감을 잡지 않고, 남으면 아래 **Codex 여유 작업**을 쓴다.

**Codex 여유 작업** (본 작업이 결정 대기로 막혔을 때, 위에서부터)
1. Claude 결과물 교차 검토: 아트 에셋을 A2 검사기로 확인, 문서 링크·작업 ID·선행 관계가 서로 맞는지 검사
2. 테스트 보강: 저장 호환, 의뢰·시세 계산, 이동 검사 자동화
3. A3a 감사 결과를 바탕으로 옛 그림 의존을 줄일 준비(교체 지점 목록, C6 사전 작업)
4. 성능·구조 정리(동작 변화 없는 리팩터링, 결과는 테스트로 확인)
5. Claude가 쓸 검토 자료 미리 만들기: 단계별 diff 요약, 화면 캡처 스크립트

**사용량이 남을 때.**
- Claude: ① Codex 아트 제출물의 규칙 확인(요청 시) ② Q1 구현 검토 ③ D10 효과표 판단(Codex 계산 후) ④ A3b 판정 ⑤ 끝난 단계 검토
- Codex: ① A2 ② R1 ③ A2b ④ A6 ⑤ R6 ⑥ Q1 구현 ⑦ A5 ⑧ C1 시험(사람 NPC 3명) ⑨ C2·C3 시험(기와집·나무) ⑩ A3a ⑪ R2 수치 계산 ⑫ B1 → E1·B2. 그 뒤에는 Codex 여유 작업

**한쪽 사용량이 바닥났을 때.** 다른 쪽은 자기 갈래를 계속하고 상대 작업을 대신 하지 않는다. 하던 작업은 `진행 중`으로 두고 작업 기록에 멈춘 지점을 한 줄 남긴다.

**동시에 돌릴 때.** Codex는 `git worktree`로 만든 `codex/<작업 ID>` 브랜치에서, Claude는 main에서 작업한다. Codex가 작업을 끝내면 **Claude가 테스트를 돌려 확인한 뒤 main에 합친다**(2026-10-24 사용자 지시: Claude가 할 수 있는 일은 묻지 않고 바로 진행). 겹치는 파일은 `Plan.md`와 `WorkLog.md`뿐이지만, 같은 곳에 줄을 더하면 git 충돌이 난다(A2 합칠 때 실제로 났음). 그래서:
- **Codex는 작업을 끝내고 보고하기 전에 최신 main을 자기 브랜치에 합친다.** `Plan.md`는 main 내용을 살리고 자기 작업 행의 상태만 반영, `WorkLog.md`는 양쪽 줄을 모두 남긴다. 그러면 main에는 충돌 없이 합쳐진다.
- 합치기 전 확인에서 문제가 나오면 Claude는 합치지 않고 작업 기록에 이유를 적어 Codex에게 돌려준다. 끝난 작업 폴더(worktree)는 Codex가 다음 작업을 시작할 때 정리한다.
- **다음 작업은 최신 main에서 새 브랜치(`codex/<작업 ID>`)로 시작한다.** 끝난 작업의 브랜치에서 이어 하지 않는다.
- 다른 쪽 영역을 고쳐야 하면 직접 고치지 말고 작업 기록에 요청을 남긴다. 작은 오타·링크 수정은 예외.

평판 데이터 R1은 D10 수치 없이도 시작할 수 있다. 확정된 것은 단계 이름과 시작 단계(출신 문명 우호·다른 문명 및 중앙 마을 중립), 평판 단위(스타팅 지역 문명별·중앙 마을별)이며, 단계별 점수 경계·증감량은 확정되지 않았다. 이 수치를 임의 확정하지 않고 데이터·저장부터 구현한다. 옛 저장의 출신 판별·평판 초기화 정책도 확인한다.

R6의 판단 사항은 Claude가 [돈·신용·평판](Standing.md) 2절 'R6 결정'으로 정했다(2026-10-24). Codex는 그대로 구현하고, 완료 기준을 만족하면 Q1 구현으로 넘어간다.

A2는 등록 목록 검사와 배치 결과 검사를 구분한다. 현재 생성기의 `stamps` 기록은 최종 맵 JSON에 포함되지 않는다. 개체 ID·배치 위치·전체 구성과 최종 타일의 대조 등 실제 배치를 검증할 근거가 필요하다. 용도 검사는 명시된 지형·배치 규칙 범위에서 수행하며, 그림체·미적 적합성은 자동 합격으로 판정하지 않는다.

아트 비교 검사는 이미 [아트 기준](ArtGuide.md) 4절에 있다. A1 승인본과 실제 플레이 크기의 합성/게임 화면을 비교 자료로 쓰되, 새 승인 완료를 뜻하지 않는다. B2의 생성 로직 개발과 승인된 A4 에셋으로 화면을 검증하는 완료 시점을 구분한다. 상세 재검토 근거는 [Codex 분석 재검토](Validation/Codex-Analysis-Review-2026-10-24.md)에 있다.
