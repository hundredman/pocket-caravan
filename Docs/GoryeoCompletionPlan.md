# 고려 지역 완성 계획

> **현재 구현 추적:** [개발 진행표](DevelopmentStatus.md)를 먼저 확인한다. 아래 검토 당시의 ‘4맵·마을2·시설/낙하 제거 미구현’은 이전 기준선이다. 이번 구현은 6맵·수도1+마을4·로컬 시설3종이며, 사용자 후속 확인에 따라 감속을 나타내는 시각적 흔들림은 유지한다. 기획/검증/미완료는 진행표에서 구분한다.

> **10월17일 최신 기준:** [변경 요약](DesignUpdate_2026-10-17.md)을 우선한다. 주행 낙하 제외·감속 중심과 정보/적재/판매/범용 이동 역할이 후속 결정이다. 아래 이전 구현·자동 주행·회수 기록은 새 목표의 승인/완료를 뜻하지 않는다.

기준일: 2026-10-15. 사용자 담당인 기본 2D 고려 지역을 먼저 완성하고, 다른 지역 제작의 기준으로 삼는다. 아래 세부 경험·수치·범위는 제안이며 구현 완료나 팀 합의가 아니다. 초기 4주 MVP의 2~4명 검증과 최종 MMORPG 규모의 다중 접속 목표를 구분한다. 사용자는 최신 계획에 따른 고려 본편 개발 재개를 요청했다. [고려 제작 명세](GoryeoRegionSpec.md)의 수도1+마을 최소4·시설 해금을 필수 범위로 적용한다. 미확정 제안의 일괄 구현과 구분한다.

후속 요청으로 팀에게 보여 주고 수정할 고려 프로토타입의 지역 개선을 재개했다. 최신 적용은 [개경 수도 도착·물류 동선 개선](GoryeoPrototypeReview.md)이다. 지역 배치·기존 연출만 보강했으며 전체 제작 구조/경제/온라인의 일괄 변경은 하지 않았다. 최종 미술·지역 완성 승인은 별도다.

2026-10-16 사용자 확인 마감은 11월 초다. 실행 작업은 [개발 작업 목록](ImplementationBacklog.md)의 GY/MV/MAP 항목, 날짜/담당 배정안은 [개발·검증 일정](DeliveryPlan.md)을 따른다. 지역 실명 담당은 확인됐으며, 실제 마감일·공통 기능 담당/가용시간 확인 전 일정 확정으로 읽지 않는다.

전체 공간·역사 모티브·각색·흥미 요소의 누락표는 [고려 전체 디자인·고증 검토](GoryeoDesignReview.md)를 함께 본다. 원본 시대는 8~15세기 상인 문화가 만나는 가상 교역 세계이며 단일 12세기 복원이 아니다. 이번에 상업 백과와 공급지/손익 설명을 적용했으나, 수도 대표 아트·현장 발견·주막 기능·무설명 왕복/실패 복구 검증은 아직 남아 있다.

맵 설계의 수정·재사용, 환경/고증 자료 적용, 팀 제작 도구 선택은 [지역 제작·수정·확장 설계안](RegionAuthoringPlan.md)에 정리했다. 지역 등록부/공용 목록 소비는 후속으로 구현됐다. 다음은 한 맵 선택 생성과 수작업 보존·지도/경제거리 분리·다섯 거점 제작 예제 보완이다. 현재 안전한 시각 편집 기능이 완성되었다는 뜻은 아니다.

## 1. 완료할 경험

플레이어가 긴 튜토리얼 없이 물건을 사고, 경로와 운반 수단을 고르고, 고려 내 다른 거점에 팔고, 다음 거래를 스스로 계획한다. 수도 개경1곳과 수도 외 최소 네 마을을 완성하고, 마을 등급·개인 신용에 따라 시설/고급 거래를 실제 이용할 수 있어야 한다. 각 거점은 자유롭게 방문하고 기본 매매할 수 있으며 역할·외형·소리가 달라야 한다. 지역 완성은 맵 장식과 스토리 완료만으로 판정하지 않는다.

초기 검토 근거: `Tools/MapGen/maps.py`, `gaegyeong.py`, `PlayerController.cs`, 개발 기준 문서, 기존 `output/2d-maintenance/*-after.png`. 기존 캡처는 현재 실시간 플레이 관찰이 아니다. 초기 확인 당시 Unity MCP가 응답하지 않았으나, 이후 복구하여 아래 9절 이후의 Play 검증을 수행했다. 최신 연결 상태는 작업 시 다시 확인한다.

## 2. 제작 순서

| 단계 | 작업 | 통과 기준 |
|---|---|---|
| 1. 기준 보존 | 현재 변경·씬·저장 상태 기록, 별도 시험 저장, 기준 빌드·동일 구간 캡처 확보 | 기존 튜토리얼과 시험장 모두 재현 가능. 생성 전 씬 수작업 차이 확인 |
| 1a. 지역 구조 | 수도1+마을 최소4의 등급·생산/소비·시설/해금·출구표 작성. 기존 수도1+마을2에서 최소2마을 추가 | 길/장식/씬 수와 거점 수 분리. 다섯 townId·기본 거래·실제 시설 기능, 자유 왕복 |
| 1b. 시설 성장 | 마을 기본 등급과 개인 신용으로 시설/고급 거래 판정, 기존 거래량 성장·Q7/저장 재검토 | 저신용/문턱직전/충족·재접속·다른 유저 권한 검사. 기본 매매/재기 유지 |
| 2. 본게임 이동 | 예성 길의 일부를 두 경로로 구성. 짧은 도보 샛길과 길지만 수레에 유리한 큰길. 분기 전에 상태를 알 수 있게 표시 | 동일 출발·도착·화물로 양쪽을 직접 비교. 화물·수단을 바꾸면 선택할 이유가 달라짐 |
| 3. 교역 순환 | 고려 내 거점마다 생산/소비 역할, 구매·판매 전 정보와 결과 정산. 되돌아올 화물도 마련 | 퀘스트 없이 구매→운반→판매→다음 거래 가능. 모든 왕복이 자동 흑자일 필요는 없음 |
| 4. 대표 구역 아트 | 나루의 선착장~마당~출구를 먼저 완성. 동일한 화면 크기에서 검토한 뒤 수도·생산 마을에 적용 | 축척·팔레트·윤곽선 일관. 끊긴 길·잘린 타일·가려진 출입구 없음 |
| 5. 지역 개성 | 개경은 성문·시전 밀도, 닥목은 생산 공정·재료 적치, 나루는 수변·운송 흔적 | 지명 UI 없이도 세 지역의 기능과 분위기를 구별할 수 있음 |
| 6. 전달과 회귀 | 공통 지역 데이터·프리팹·검증 도구·제작 예제 정리 | 다른 팀원이 고려 코드를 복사 수정하지 않고 다른 지역 하나의 거점·장터·출구를 연결 |

각 단계에서 실제 게임 화면과 짧은 플레이로 검토한다. 모든 맵을 한꺼번에 재생성하거나 새 시스템을 대량 추가하지 않는다. 단계 2~3부터 네트워크 담당과 상태/명령 경계를 공유하고, 지역 완성을 기다렸다가 멀티 작업을 시작하지 않는다.

## 3. 이동의 재미

- 분기 이전에 노면, 거리, 휴식 거점, 현재 화물 상태를 읽을 수 있게 한다. 위험을 모른 채 맞는 벌은 선택의 결과로 느끼기 어렵다.
- 주행 낙하와 정차 안정화는 제외한다. 노면·적재 감속을 비교하고, 큰길/샛길의 실제 왕복 효율과 선택 이유를 시험한다. 기존 화물/원가/의뢰의 저장 이주가 선행되어야 한다.
- 경량 도보는 샛길, 중량 수레는 큰길이 유리한 상황을 목표로 하되, 매번 두 길을 강제로 번갈아 쓰게 하지 않는다.
- 풍경은 나루의 개방감→수림의 좁은 구간→다리와 물소리→성문과 시전으로 변화시킨다. 맵 면적 증가만으로 거리를 표현하지 않는다.
- 주막은 긴 대사를 읽는 곳에 그치지 않고 휴식 또는 경로 정보 중 하나를 실제로 제공한다. 새로운 보급·날씨·전투 시스템 전체를 이번 필수로 추가하지 않는다.
- 작은 발견 지점은 돌아갈지 판단할 만한 정보나 경치를 제공한다. 반복 리스폰 현금 보상을 남발해 교역 수익을 대체하지 않는다.

## 4. 화면과 손맛

현재 원본은 길·거점 구조가 읽히지만 풀과 소품이 균일하게 흩어지고 지역별 표지가 약하다. 기존 캡처에서 받은 시각적 판단이며 최종 게임 화면 재검토가 필요하다.

우선은 나루의 하역 짐·곡물 적치·빈 수레·주민 행동을 선착장과 장터 주변에 묶고, 생활 동선을 연결한다. 꽃·상자 수를 전역에 늘리는 방식은 피한다. 고려의 정체성은 핵심 지붕·성문·간판·생산 소품에 일관되게 적용하고 실제 역사 재현 수준은 팀이 별도 결정한다.

물결·갈대·짧은 NPC 작업 동작, 바퀴·발걸음의 노면별 소리, 물가/마을/시장 주변음으로 이동 리듬을 만든다. 이동 반응·충돌·수레 가독성·상호작용 거리·그림 정렬을 먼저 고친 뒤 장식을 더한다. 고정 시간 HUD 제거와 대사 페이지 분할은 유지한다. 실제 게임 배율에서 통행과 상호작용 대상이 잘 보여야 한다.

## 5. 다른 지역에 전달할 제작 단위

- 공통: 장터/출구/표지판/생산 소품/휴식 상호작용 프리팹과 데이터 형식.
- 지역 데이터: 안정적인 region/town/item/exit ID, 지도 좌표와 가격용 거리 구분, 스폰·양방향 연결, 생산·소비 정보.
- 표현 데이터: 대표 팔레트, 랜드마크, 소리, 소품 묶음, NPC 외형/행동. 거래 코드에 지역명 분기 추가하지 않기.
- 검증: 맵 통행/스폰/상호작용 접근성, 나무 묶음, 출구 연결, 대사 넘침, 거래·운반·왕복 플레이.
- 원본 기준: 현재는 Python 원본→JSON→Unity 씬 생성. 씬에서만 수정한 사항은 재생성으로 사라질 수 있으므로 보존/원본 반영 절차부터 정한다.
- 온라인 대비: 지역 제작자가 로컬 지갑/공유 시간/시장 재고를 직접 바꾸는 새 코드를 늘리지 않는다. 현재 서버 연동은 미구현이며 담당자와 명령 경계를 합의한다.

## 6. 작은 플레이 테스트

팀원 3명이 설명 없이 같은 초기 자금·화물 조건으로 플레이하고, 다음 회차에 도보/수레 또는 화물량을 바꾼다. 다음을 기록한다.

1. 첫 구매와 판매를 스스로 마쳤는가? 막힌 지점과 도움 횟수.
2. 어떤 길을 왜 선택했는가? 수단/적재 조건 변경 후 선택 이유가 달라지는가?
3. 걸리는 시간, 감속·우회·정지 이유와 거리, 거래 손익.
4. 화면에서 목적지와 노면 조건을 미리 알았는가? 수도와 네 마을의 역할/등급·시설 이용 조건을 구별했는가?
5. 재이동을 원한다면 새 판단 때문인가, 단순한 보상 때문인가? 지루했던 구간을 직접 지정하도록 한다.

재미를 수치 하나로 통과시키지 않는다. 같은 문제를 여러 명이 겪으면 원인부터 수정하고, 전후 동일 조건으로 비교한다. 테스트 인원이 작으므로 일반 이용자 전체의 선호로 확대하지 않는다.

## 7. 도구와 모델

당장 필요한 것은 Unity 편집/콘솔/씬 상태/스크린샷 확인 수단, 기존 맵 생성·검증 도구, 버전 관리와 플레이 기록이다. Unity MCP는 설정 존재와 실제 Editor 연결 성공을 구분해 재확인한다. 공식 Unity Profiler로 실제 플레이의 병목을 확인하고, 네트워크 프로파일은 연결 기능 구현 뒤 별도 확인한다. 새로운 MCP 설치는 이번 문서 작업에서 하지 않았다.

기존 픽셀 에셋은 편집·재조합을 우선하고, 새 이미지 생성은 아트 방향 비교나 대표 소품 초안에 선택적으로 쓴다. 런타임 타일은 축척·경계·팔레트·라이선스·충돌을 직접 검증해야 한다. 이미 설치된 2D Aseprite 임포터는 편집 앱 자체가 아니다.

모델 변경은 필수가 아니다. Sol로 작게 구현→Unity 확인→플레이 피드백을 반복하고, 지역 구성과 공통화·멀티 경계가 복잡하게 충돌하거나 반복 수정이 해결되지 않을 때 Astra의 독립 검토를 고려한다. Astra 선택이 재미나 아트 일관성을 보장하지 않는다. 새 채팅은 작업 범위 정리에 도움이 될 수 있으나 모델 변경의 안정성을 보장한다는 공식 근거는 확인하지 못했다.

공식 모델 안내: [GPT-6 Astra](https://developers.openai.com/api/docs/models/gpt-6-astra). 공식 안내상 복잡한 추론·코딩 등에 적합하다. 이 프로젝트에서 Sol 대비 개선 폭은 측정하지 않았다. 현재 모델/추론 설정은 사용자의 선택을 유지하며 새 채팅을 자동 생성하지 않는다.

## 8. 새 채팅이 필요할 때 전달할 문장

> PocketCaravan 저장소의 Docs/README.md, Docs/HolisticDesignReview.md, Docs/GoryeoCompletionPlan.md를 먼저 읽어줘. 목표는 내가 담당한 기존 2D 고려 지역을 다른 지역의 제작 기준으로 완성하는 것이다. 최신 요청은 정리한 계획에 따라 고려 본편 개발을 이어가는 것이다. 수도1+수도 외 최소 마을4, 등급/신용별 시설 이용을 누락하지 말고 Docs/GoryeoRegionSpec.md와 FullRequirementsReview_2026-10-17.md를 함께 읽어줘. 초기 4주 MVP의 2~4명은 최종 정원이 아니며 최종 제품은 MMORPG 규모의 다중 접속 교역 세계를 목표로 한다. 현재 나루·예성 길·개경·닥목은 수도1+마을2+길1뿐이다. 추가 최소2마을·시설·시나리오와 실제 교역 경험, 제작 과정, 권한/복구 경계를 검토하고 G1~G5 관문으로 근거를 모아줘. 기존 변경·저장·3D 실험은 보존하고 구조/수치 일괄 변경이나 새 프로토타입은 시작하지 마. 사용자 담당을 전체 서버 개발로 바꾸지 말고, 제안·구현·실제 검증 결과를 구분해줘.


## 9. 예성 길 1차 적용 — 2026-10-15

구현: 기존 Route01에 숲길/큰길 분기·합류와 작은 목교 추가. 숲길·목교는 등급 1, 주막과 기존 다리를 지나는 큰길은 등급 3으로 설정했다. VehicleData와 화물 낙하 수치는 변경하지 않았다. 갈림길과 합류점 안내, 주모의 경로 안내를 보강하고 지형 지도도 갱신했다. 고려 내부 연결이며 다른 문명을 인접 배치한 것이 아니다.

Unity MCP는 Codex 설정을 기존 Editor의 Stdio 방식에 맞춰 복구했고, 재시작 후 실제 도구로 씬 조회·생성·Play 검증을 수행했다.

검증: 전체 맵 회귀 검사 58개(이정표 접근성 포함), 경로 선택 검사 4개 통과. Unity Play 중 실제 PlayerMotor/PlayerController를 수동 Tick해 같은 화물 무게 5로 비교했다.

| 수단 | 숲길 | 큰길 |
|---|---:|---:|
| 등짐 | 14.26초 | 16.06초 |
| 손수레 | 15.15초 | 13.81초 |

위 시간은 분기점부터 합류점까지 정해진 직교 경로를 120Hz 이하 간격으로 자동 주행한 결과다. 가감속·충돌·걷기 흔들림·체력 회복은 본편 코드를 사용했으며, 달리기·자유 대각선 조작·실시간 NPC 방해·낙하 후 회수의 재미를 검증한 것은 아니다. 네 조합 모두 완주하고 화물 5개를 보존했다. 본편 저장·다른 세 지역 씬·기존 시험장·빌드 목록·WorldIndex는 작업 전후 해시가 같다.

확인: Unity에 열린 `Assets/PocketCaravan/Scenes/Goryeo/Route01.unity`에서 Play. 나루 방향의 서쪽 입구에서 갈림길 표지판을 보고 북쪽 숲길 또는 주막 큰길을 선택하고 개경 방향 북쪽 출구로 이동한다. Space로 이정표와 주모에게 상호작용한다. 자동 검증용 화물/수레 변경은 저장된 씬이나 본편 저장에 반영하지 않았다. 기존 이동 시험장의 무료 수단 변경 기능은 해당 시험장에서만 제공한다.

증거: `output/goryeo-route/runtime-validation.json`, `route-choice-validation.json`, `preservation-after.json`, `route-final.png`. 고려 지역 전체 완성이나 이동 재미의 최종 승인으로 간주하지 않는다. 다음은 직접 플레이 피드백 후 교역 왕복과 나루 대표 구역의 시각·소리·생활감 개선이다.


## 10. 본편 운반 가독성과 검토 빌드 — 2026-10-15

손수레 선택 시 본편 플레이어 뒤에 수레가 보이고 적재율에 따라 상자 0~3개가 나타난다. 운반 속도·용량·충돌·낙하는 기존 시스템이 담당한다. HUD는 짐을 실어도 발밑 노면을 항상 보여 주며, 흔들림 단계에 따라 걷기/큰길/정지 대처법을 안내한다. 시험장에서는 자체 수레와 중복 표시하지 않는다.

비시작 씬을 직접 실행할 때 저장 파일이 없는 경우에도 자동 저장을 차단하도록 보완했다. Mac 프리뷰 빌드는 기존 본편 저장과 파일을 분리하고 본편 고려 네 맵만 포함한다. 플랫폼 서명/공증과 Windows 지원 모듈은 이번 빌드에 포함하지 않는다. 소스는 검토 브랜치/PR, 실행 파일은 GitHub 프리릴리스로 전달한다. 빌드 성공 여부와 링크는 실제 업로드 결과로 확인한다.

실제 Player 빌드에서 `GUIStyleState.scaledBackgrounds`의 에디터 전용 API 호출로 컴파일이 실패하는 기존 문제를 발견해 `UNITY_EDITOR` 조건으로 분리했다. 에디터 Play 검사와 실행 파일 빌드 검사를 구분한다.

## 11. 교역 판단과 마을 생활감 — 2026-10-15

구현: 장터에서 품목을 선택하면 산지, 보유 화물의 평균 원가, 이곳 판매 시 개당 손익과 다른 장터에서 직접 확인했던 판매가를 비교한다. 이번 방문의 판매 개수·매출·손익도 표시한다. 재고·잔고·용량이 부족한 구매와 의뢰 짐 거래를 막고, 외지 물건 마지막 한 개를 판매할 때 목록 순회가 깨지던 문제를 수정했다. 판매된 외지 상품은 해당 시장의 알려진 재고 목록에 남는다.

L키 공통 장부는 장터를 열거나 거래할 때 확인한 가격을 기록하며 저장된다. 미방문 지역의 가격을 원격 조회하지 않는다. 외지 시세는 마지막 확인값·첫 한 개 기준이고 도착 때 달라질 수 있다. 개별 관측 시각/신선도와 고려 출신 특혜는 아직 없다. 이전 저장에는 장부가 없어도 불러오기를 지원한다.

나루에는 적치장과 선착장을 왕복하는 짐꾼, 운송 소품과 안내판을 보강했다. 닥목에는 종이 건조대·재료 적치·접근로와 작업 일꾼을 넣었다. 두 마을 물가에 거리별 주변음을 배치했다. 작업자는 통행을 막지 않는 연출이며 생산 경제를 새로 구현한 것은 아니다. 공통 빌더의 `worker`/`ambience` 데이터로 다른 지역에서도 재사용할 수 있다.

검증: 맵 통행·출구·작업 경로 검사 66개, 기존 경로 선택 검사 4개. Unity 실행 중 실제 구매/판매·원가 보존·장부 관측/JSON 호환·작업 왕복·소리 로딩 등 15개 검사 통과. 실제 L키 열기와 Esc 닫기, 입력 차단 해제, 기존 저장의 잔고 복구와 빈 장부를 확인했다. 물가 음량 감소와 음소거도 별도 검증했다. 장터와 장부 화면의 잘림 여부를 캡처로 확인했다. 테스트 재화는 격리 세션 메모리에만 적용했다.

근거는 로컬 `output/goryeo-life/`의 검사 코드·결과와 `naru-harbor.png`, `dakmok-workshop.png`, `capital-market-final.png`, `portable-ledger.png`다. 결과는 로컬 기능 검증이며 반복 이동 재미, 경제 밸런스, 서버 권한 및 2~4명 온라인 검증 완료를 뜻하지 않는다. 이번 실행 파일은 로컬 검증용으로만 만들고 기존 배포 프리릴리스는 갱신하지 않는다.

Mac Player 빌드 성공(오류 0, 경고 1, 약 14초). 경고는 Unity Cloud 토큰이 없어 네이티브 심볼을 업로드하지 못한다는 내용이다. 로컬 결과는 `Builds/validation-goryeo-life/build-report.json`과 `PocketCaravan.app`이다. 본편 저장·기존 길/수도/시험장 씬·빌드 목록·WorldIndex는 작업 전후 해시가 같음을 확인했다. 다음 플레이 평가는 이 장부와 경로 선택을 이용해 설명 없이 왕복 교역을 마칠 수 있는지 확인한다.
